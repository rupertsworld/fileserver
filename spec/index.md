# fileserver spec

This is the entry point and source of truth for the public behaviour of
`fileserver`. Every spec file must be reachable from this one. The server
exposes one directory as resources at real URLs so a browser page, script,
or agent can read, list, write, edit, delete, and watch files over HTTP and
WebSocket without a separate backend. A file can be used as an `<img src>`,
a ranged download, or a cached asset, and a client can refetch after a
change signal. One instance serves one directory; a host can mount several
instances under different names. It is built for
[Television](https://television.run).

## Contract

- [Server](server.md) — the routes, representations, change
  stream, programmatic API, and extension seam.
- [CLI](cli.md) — invocation, options, output, errors, and config storage.
- [Skill](skill.md) — what the bundled consumer skill must cover.
- [Testing](testing.md) — how the package is verified.

## Project structure

Source lives in `src/`, tests in `test/`, the bundled consumer skill in
`skill/`, and the contract in `spec/`. Documentation that is not
spec lives under `docs/`. Docs cite the spec clauses they justify, never
the reverse.

## Distribution

The npm package is `@rupertsworld/fileserver` and its CLI binary is
`fileserver`. The package is built from this repository and is not published
to a registry. It includes the consumer skill and exports the server and its
extension types for embedding in another process (see
[the API](server.md#api)). A wire change and the corresponding skill
update land in one commit.

## Approval boundary

The spec is the approval boundary for public behaviour. No route,
body, status, header, or flag may change without approval of the
corresponding spec change before implementation. Error message
wording is not part of the boundary.

## Trust model

`fileserver` binds localhost by default, requires no request authentication,
and leaves CORS wide open so browser pages from any origin can call it
directly. The network boundary is the protection; a host that needs origin
or caller policy applies it in front. Browser local-network rules may still
block or prompt a public page reaching a loopback server; the browser
controls that access.

## HTTP conventions

Every response carries `Access-Control-Allow-Origin: *` — safe alongside
no authentication because `*` forbids credentialed requests by definition.
An accepted `OPTIONS` preflight returns `204` with no body, carrying the
allowed methods and request headers, a cache max-age, and
`Access-Control-Allow-Private-Network: true` when requested by a browser
that sends the legacy header. [Errors](server.md#errors) specifies when a
preflight is accepted; [CORS](server.md#cors) gives the header values.

Error bodies are `{ "error": "<message>" }`.

## Implementation

Node ≥ 24, TypeScript, Express. These are the mechanisms behind the
contract; the contract, not the mechanism, is the approval boundary. The
build produces the shipped `dist` and runs through `pretest`. The implementer
chooses the internal module structure. The server uses `ws` for WebSockets
and `chokidar` for filesystem changes.

- **Media types** come from `mime-types` (the `mime-db` dataset).
- **Writes** go to a temporary file in the target directory and are
  renamed into place. That makes a write atomic to readers and leaves the
  existing file intact when a transfer fails; a failed write removes its
  temporary file.
- **Confinement** is canonical-path checking. The root is resolved once at
  startup. For each request the deepest existing component of the path is
  resolved with `realpath`, checked to lie beneath the resolved root, and
  each existing component is `lstat`ed to reject symbolic links; anything
  to be created is then created beneath the checked directory. Node has no
  `openat2`, so this is check-then-act; [Confinement](server.md#confinement)
  states the resulting guarantee and its limit.
- **`ETag`** is the weak size-and-mtime tag generated by Express `send`
  (`W/"<size>-<mtime>"`).
- **Streaming.** `GET` responses serving file bytes stream from disk, with
  `Range` mapped to a start/end read; `PUT` bodies stream to the temporary
  file. The buffered mutation payloads are `PATCH` documents, the files
  they edit, and the edited result, each capped at 16 MiB.
- **Temporary files** have a collision-resistant name in the target
  directory, are excluded from listings and addressing, and are removed if
  the write fails.
- **Directory listings** are built from one `readdir` with file types plus
  one `stat` per regular file.
- **Change signals** come from one watcher on the root. External events are
  debounced per path; once a path has been quiet for the debounce period,
  one dirty signal is published from the net transition and final disk state
  of that path: creation followed by changes remains `created`, deletion
  followed by recreation is `created`, an existing path that remains is
  `modified`, and a path that ends absent is `deleted`. HTTP mutations
  publish directly when their atomic change completes and suppress the
  duplicate watcher signal, so they do not wait for the debounce. Initial
  indexing does not publish events or incur the debounce delay.
- **CLI** is a thin wrapper over the exported server: parse flags, read
  the config, construct, `listen`, print, and close on signals.
